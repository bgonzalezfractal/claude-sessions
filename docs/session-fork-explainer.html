Two sessions from one copy: forked conversations, one live set of files

Copying a session forks the conversation. It doesn't fork the files. Both sessions work on the same git branch in the same checkout, so each one sees the other's edits the next time it reads a file. What goes stale is each session's memory of a file, plus the things that aren't files at all.

1 · What forks and what stays one

Top half: each session has its own conversation, context, memory, task list and checkpoints. Bottom box: there's only one of each, and both sessions read and write it.

2 · The files are live, the memory of them is stale

live The files

Like two developers on the same branch in the same folder. When NEW saves a file, OLD reads the new version the next time it opens it.

nirvanav0/ one branch, one checkout NEW saves inbox.py OLD opens inbox.py → sees NEW's version

stale What each session remembers

What a session read an hour ago stays in its context. It answers and edits from that copy until it reads the file again.

OLD context: inbox.py as of 14:19 disk: inbox.py as of 15:40 → re-read before editing or answering

3 · Your protocol: split the files, tell each session what the other does

One session analyses and writes HTMLs, the other edits code. When both work on code they aim at different files, and each prompt says "an agent is working on X while you work on Y". It's the same model that kept the large workflows consistent: an owner per module, re-read before editing.

The "no" rows don't need anything written into logs or files. Each one is one more line in the prompt you already write.
